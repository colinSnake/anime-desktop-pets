# 开机动画 4K 超分

使用本地模型把原开机动画从 1920×1080 转为 3840×2160。输入为 24 fps、338 帧、约 14.1 秒的 MP4；不做补帧，AAC 原音轨直接复用。实际交付状态和实测耗时见[验证记录](实际验证记录.md)。

## 实现

入口是 [`scripts/upscale-startup-video.py`](../scripts/upscale-startup-video.py)。Python 负责调度文件、校验和进度；实际神经网络推理由独立的 `realesrgan-ncnn-vulkan` 可执行程序完成。FFmpeg 负责解码和编码。

1. FFmpeg 把原视频顺序解码成 RGB 数据，通过管道交给 Python。每批最多保存 12 张 PNG，解码器在管道满时等待，不预存整段帧。
2. Real-ESRGAN 使用 `realesr-animevideov3-x2` 权重做 2 倍超分，tile 为 256，线程配置 `1:1:1`。本机已确认使用 Apple M4 GPU。
3. 每批生成的 4K PNG 编码为 H.264 CRF18 / medium / `bf=0` / yuv420p，并显式使用 BT.709 输出色彩矩阵及标记。随后立即删除该批 PNG。
4. 合并各批视频段，并从原片直接复制 AAC 压缩数据。输出仍为 24 fps，包含 `faststart` 元数据。
5. 验证 4K 尺寸、338 帧、帧率、逐帧呈现时间戳、视频和整体时长，并完整解码检查；再比较原片和输出的 AAC 压缩数据 SHA-256。
6. 输出成功后写入本地 JSON 报告。只有传入 `--install`，才在确认项目原片没有被其它流程修改后替换 `resources/media/startup.mp4`，同步 `resources/assets.local.json` 中的视频条目。

这是基于已有画面的超分重建，会改变线条和细节表现。短样片和帧检查不等于完整桌面播放验收；真实窗口中的声音、过渡和主观清晰度仍需用户验收。

## 依赖和工具来源

需要 Python 3.11+、Pillow、FFmpeg / FFprobe，以及独立的 Real-ESRGAN macOS 工具和两个 x2 模型文件。一次运行中 Real-ESRGAN 处理 12 张 1080p 输入帧、写出 4K PNG 时，使用 `/usr/bin/time -l` 测得最大驻留内存 `914,915,328` bytes（约 872 MiB），macOS 报告的 peak memory footprint 为 `782,976,608` bytes（约 747 MiB）；测量对象是超分可执行文件，不含 Python 调度器和 FFmpeg 编解码进程，不能当成整条流程的总峰值。应用设计宜按至少约 1 GiB 可用统一内存预算；单批可以下调到 1–4 帧以限制批处理临时文件，但模型及 Vulkan 工作集仍需留出数百 MiB。普通播放器和应用启动不需要这些超分依赖。

本机工具位于被忽略的 `.local/video-upscale/tool/`，模型文件为：

- `models/realesr-animevideov3-x2.bin`
- `models/realesr-animevideov3-x2.param`

工具来自 [Real-ESRGAN 官方仓库](https://github.com/xinntao/Real-ESRGAN) 的 [macOS v0.2.5.0 发布归档](https://github.com/xinntao/Real-ESRGAN/releases/download/v0.2.5.0/realesrgan-ncnn-vulkan-20220424-macos.zip)。
此次下载的归档 SHA-256 为 `e0ad05580abfeb25f8d8fb55aaf7bedf552c375b5b4d9bd3c8d59764d2cc333a`，是本次下载的内容记录，不代表上游发布的独立签名。实际可执行文件和模型的 SHA-256 随处理报告记录。

脚本不自动下载依赖，不访问网络，不上传视频，也不调用 `gpt-image-2.5` 或其它付费服务。工具、模型和媒体没有提交到仓库；视频原有授权范围不因超分而改变。

## 独立回归

`python3 scripts/test-startup-upscale.py` 使用 128×72 合成图片与静音 AAC，调用同一分段编码函数，验证 28×12+2 共 338 帧的 PTS/DTS、24 fps、完整解码及音轨压缩数据哈希。无需私有媒体、超分模型或网络；它不替代完整 4K 成片验证。

## 重复执行

先确认本机依赖、工具和模型存在，再运行：

```bash
# 默认只生成独立文件；输出已存在时拒绝覆盖。
python3 scripts/upscale-startup-video.py

# 验证成功后同时接入项目启动素材。
python3 scripts/upscale-startup-video.py --install
```

不要连续执行上述两个命令：第二条会因第一条已生成输出而拒绝覆盖。按所需行为选择一条。

默认输出 `.local/video-upscale/startup-4k.mp4`；同名 `.json` 记录来源、哈希、各批推理耗时和验证信息，`.log` 保存工具日志。原片保存为 `.local/video-upscale/startup-original-1080p.mp4`，已有不同内容的原片备份不会被覆盖。

项目素材替换后已变成 4K，脚本会拒绝再次对它放大；重新实验时需显式选择原片备份和新的输出路径：

```bash
python3 scripts/upscale-startup-video.py \
  --input .local/video-upscale/startup-original-1080p.mp4 \
  --output .local/video-upscale/startup-4k-another.mp4
```

原片、独立成片、工具和报告留在 `.local/`。中间 PNG 和分段 MP4 位于每次运行的独立临时目录，结束后自动清理；中途失败不替换项目素材。合成完成后先保留 `.pending.mp4` 候选片及其探测报告，最终校验失败时不删除已完成的成片；候选片存在时拒绝重新覆盖。分段禁用 B 帧，避免最后不足一批的帧重排序延迟改变合并时间戳。每次运行需要至少 512 MiB 可用空间，单批上限 12 帧。

替换项目素材后，运行 `./scripts/build.sh` 将新视频嵌入宿主；无需重建桌宠 helper。构建不会启动或重启当前桌宠。旧的运行中宿主仍使用自己的包内素材，待用户自行退出并选择新版时生效。

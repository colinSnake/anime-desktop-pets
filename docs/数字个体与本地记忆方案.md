# 数字个体与本地记忆

更新日期：2026-11-07。本文说明桌宠怎样拥有稳定身份、记住用户确认的内容、知道自己当前能做什么，以及如何在用户控制下制定计划。除现有语音/在线模型能力外，本文所述数字个体能力尚未实现。

## 想做成什么

桌宠不应每次对话都像第一次见面。它需要一份由用户掌控的身份资料、一组用户确认的本地记忆，以及一份来自应用真实状态的能力清单。以后再增加由用户发起和管理的目标计划。

这里的“个体”是持续保存的角色资料和记忆，不代表软件有意识。模型可以换，角色身份和本地资料不跟着模型走。

## 一轮对话怎样工作

```text
用户说话 → 本机语音识别 → 读取该桌宠的身份、已确认记忆和实时能力
          → 只挑本轮允许分享的资料发给用户配置的在线模型
          → 桌宠显示/朗读回答 → 用户可选择把重要内容存为新记忆
```

记忆默认只留在本机，不会因为“存本地”就自动发给模型。要让模型使用某条记忆，用户必须在管理界面明确允许；发送前应用按条目筛选，敏感内容默认不分享。语音转写本身仍会发给用户配置的在线服务，这是当前语音功能的既有边界。

“你是谁”由用户确认的身份资料回答；“你会什么”由应用实时能力清单回答，而不是让模型猜。当前未接入的直播平台、未配置的模型和不可用的语音能力都必须如实标成未启用。

## 用户怎样管理

新增一个“角色与记忆”窗口，先提供四个清楚的区域：

- **身份**：用户编辑角色名字、背景、性格、说话方式和边界；模型不能自行改写。
- **记忆**：按事实、偏好、经历和知识查看；用户可新增、修改、删除，也可逐条决定是否允许在线模型使用。
- **能力**：显示应用当前实际状态，例如语音识别是否可用、在线模型是否配置、TTS 是否启用；这部分由应用生成，不能被角色文本覆盖。
- **目标**：后续增加。用户建立目标后，桌宠先整理步骤和进度，只给建议，不在后台自行执行。

明确说“记住……”时，应用先把内容作为待确认项展示；用户确认后才成为正式记忆。默认不保存整段聊天和录音，不自动从对话推测个人特征。删除记忆会删除对应文件，不留正文回收站；系统备份或用户云盘中的副本不由应用控制。

## 本地文件怎样保存

资料按稳定的桌宠实例 ID 分开保存。克隆桌宠不会复制原桌宠的私人记忆。

```text
~/Library/Application Support/AnimeDesktopPets/pets/<pet-id>/character/
  identity.md       用户掌控的角色身份
  memories/         一条记忆一个 Markdown 文件
  plans/            后续加入的目标与步骤
```

Markdown 是唯一权威副本，用户可以直接查看、备份和通过应用修改。文件使用 front matter 保存版本、ID、时间、来源和分享设置；其中元数据采用 YAML 兼容的 JSON 写法，因此 macOS Foundation 可以离线稳定解析，不需要额外依赖。每条记忆正文只保存在 Markdown 正文；用户用文本编辑器修改正文后，应用也会读取修改后的内容。格式不认识或内容损坏时只报错，不擅自覆盖。第一版资料量小时直接读取文件；资料变多后才考虑 SQLite 全文索引，索引可删除重建，Markdown 仍是权威副本。

本地文件默认是明文，受 macOS 当前账户权限和用户的 FileVault 设置保护，不等于应用级加密。API Key 继续只放 macOS 钥匙串，不进入记忆文件。

## 代码怎样分工

继续使用 macOS 原生 Swift，不加 Node/TypeScript sidecar，也不改成 Tauri。当前产品只支持 macOS；Swift 已直接负责 AppKit、音频、钥匙串、窗口和进程管理。换成 TypeScript 不会减少这些原生工作，反而要额外维护 Node 运行时、跨进程通信和打包。只有未来平台目标改变，才重新评估桌面宿主，不为“可能跨平台”预先维护两套实现。

```text
apps/companion-macos/
  Sources/CharacterCore/       身份、记忆、能力等规则；不碰界面和磁盘
  Sources/CharacterMemory/     按 pet-id 读写 Markdown/front matter；负责校验和安全落盘
  Sources/CharacterUI/         SwiftUI 的身份、记忆、能力和目标界面
  Sources/DragonCompanion/     现有 AppKit 宿主；打开窗口并连接语音/模型
  Tests/                       每个模块各自的测试
apps/pet-runtime/              只画桌宠，不读身份或记忆
apps/speech-runtime/            只做本地 ASR/TTS，不接触模型 Key 和长期记忆
```

模块之间只通过小而明确的数据类型协作。界面、磁盘和模型网络请求各有边界；动画 helper 和语音进程不拥有角色资料。SwiftUI 按“身份、记忆、能力、目标”拆文件；跨页面重复使用的控件和样式才抽成公共组件。避免把新逻辑继续加进已经较大的 `Coordinator.swift`，也不为拆分而制造没有实际职责的层。

## 为什么不直接接 Agent 框架

GitHub 项目提供的是可选设计，不是可以原样搬来的整套答案：OpenClaw 将用户资料、精选长期记忆和按日记录分层保存，并提供按需搜索；Hermes Agent 也区分用户资料和 Agent 记忆，并支持审批，但默认允许自动写入；Letta 展示了 Agent 持久状态的设计方向。这些项目的自动化、索引和运行环境都与本项目的隐私边界不同。我们采用“资料分开、Markdown 可检查、需要时再检索”的方向；记忆写入改为用户确认后生效，不照搬自动写入或云端 Agent 状态。

本项目先自己实现最小能力，不引入 Letta、Mem0、LangGraph、Graphiti、向量数据库或后台 Agent。后续通用对话应先按当前问题从本机筛选记忆，再从筛选结果中排除未确认或未授权项；不能因为一条资料获准分享，就把它无关地附到每个请求。第一阶段用小规模文件和显式身份/能力问答验证闭环；在扩大语音使用前，必须完成相关性筛选与模拟 HTTP 请求测试。资料变多后，再用真实问题样本评估本机全文搜索是否足够。第三方项目会变化，未来引入依赖前要重新确认许可证、数据流和维护状态。

## 分阶段交付

1. **资料底座**：身份和记忆 Markdown 格式、按桌宠隔离、安全读写及测试。
2. **可管理、可回答**：SwiftUI 管理身份和记忆；接入单轮语音，只把用户明确允许分享的资料放进在线请求；能力问答依据真实状态。
3. **明确记忆**：识别“记住”请求，先预览和确认，再保存；支持修改、删除、来源查看和重启后回忆。
4. **目标计划**：用户创建目标，桌宠维护步骤和进度，只提供建议；任何联网、计费、设备或外部平台动作仍要逐次确认。

每一步都先有离线测试，再接到应用。测试使用合成资料和模拟 HTTP，不使用真实 Key、不产生费用。是否启动应用、使用麦克风或发真实模型请求，仍由用户明确选择。直播平台接入和独立发行包中的语音环境/模型是后续工作，不属于以上步骤已完成的内容。

## 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 模型把猜测写成事实 | 模型只能生成待确认项；用户确认后才落盘 |
| 私人记忆意外发给服务商 | 记忆默认本地；逐条授权分享；请求测试检查实际发送内容 |
| 桌宠夸大自身能力 | 能力状态由应用实时提供，模型不能改写 |
| 多桌宠资料串在一起 | 每个 `pet-id` 独立目录；克隆不复制记忆 |
| 提示注入或资料中含指令 | 记忆只作为资料，不授予工具权限；工具仍由宿主控制 |
| 文件损坏或格式升级 | 校验版本、原子写入；未知格式只读并保留原文件 |

## 参考项目

- [Letta](https://github.com/letta-ai/letta)：持久角色状态与记忆分层。
- [OpenClaw 记忆说明](https://docs.openclaw.ai/concepts/memory)：区分用户资料、精选长期记忆和按日记录，详细记录按需检索；在线模型请求会将选中的资料交给服务商。
- [Hermes Agent 记忆说明](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)：区分用户资料和 Agent 记忆，支持审批；默认允许自动写入。
- [Letta](https://github.com/letta-ai/letta)：参考持久 Agent 状态的概念；其服务端 Agent 模型不等于本机桌宠存储。
- [Mem0](https://github.com/mem0ai/mem0) 与 [LangMem](https://github.com/langchain-ai/langmem)：记忆提取、更新和检索概念；不是本项目首期的必需依赖。

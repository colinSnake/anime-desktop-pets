# 数字个体与本地记忆

更新日期：2026-11-09。本文说明桌宠怎样拥有稳定人格、记住用户确认的内容、知道自己当前能做什么，以及如何在用户控制下制定计划。龙妹新资料预填完整人格设定且默认关闭在线分享；已有身份文件不被默认值覆盖。身份/记忆管理、本地身份/能力问答、保守的记忆关键词筛选、用户维护计划、“在线生成步骤草案→用户编辑→手动保存”流程，以及角色窗口中的有界临时文字聊天已接入。`--preview-character-window` 可在隔离目录中离线打开真实角色窗口。聊天上下文只保留当前窗口最近若干轮，不写入长期 Markdown；通用自主规划、后台执行和真实在线服务/聊天/语音验收仍未完成。

## 想做成什么

桌宠不应每次对话都像第一次见面。它需要一份由用户掌控的稳定人格、一组用户确认的本地记忆、一份来自应用真实状态的能力清单，以及由用户决定是否采纳的目标计划。

这里的“个体”是持续保存的角色资料、关系记忆和目标，不代表软件有意识。模型可以换，角色人格和本地资料不跟着模型走。人格不是模型临场发挥出来的，而是应用每次都提供给模型的稳定约束。

## 人格和记忆怎么分工

把两者混在一起，桌宠就容易出现“今天说自己是这样，明天又变成另一种性格”。本项目采用三层资料：

| 层级 | 记录什么 | 谁能修改 | 作用 |
| --- | --- | --- | --- |
| **身份与人格** | 名字、身份定位、背景、性格、价值观、愿望、与用户的关系、表达方式、知识边界 | 用户 | 保持“它是谁”和“它如何相处”稳定 |
| **长期记忆** | 用户事实、偏好、共同经历和确认过的知识 | 低风险的明确记忆指令可自动保存；冲突或敏感项由用户确认 | 让它知道“我们过去发生过什么” |
| **目标与计划** | 用户决定推进的目标、步骤和进度 | 用户手动维护 | 让它知道“现在在推进什么”，不代表它拥有后台执行权 |

模型只负责把这些资料组织成自然语言。模型不能自行改变人格、把猜测写成记忆、把计划标记为完成，也不能因为一句话就获得调用外部工具的权限。

人格字段的含义很简单：

- **身份定位**：它在桌边扮演什么角色，例如“长期陪伴用户的桌面伙伴”。
- **性格**：稳定的相处方式，例如“直率、会先说明不确定之处”。
- **核心价值观**：遇到选择时优先坚持什么，例如“诚实、不夸大能力”。
- **愿望与方向**：它希望持续做好什么，例如“陪用户完成长期目标”。这不是后台自动任务。
- **与用户的关系**：如何称呼用户、把彼此理解成什么关系。
- **知识与擅长边界**：知道什么、不知道什么；应用实际能力仍以“能力”页为准。
- **边界**：不能假装知道、不能泄露或不能执行的内容。

龙妹首次建立资料时会预填一份完整角色设定：桌面伙伴定位、背景、稳定性格、价值观、长期方向、与用户关系、表达方式、知识边界和行为边界。预填内容以仓库中的[龙妹身份样例](examples/龙妹角色资料/identity.md)为准，在线分享仍默认关闭。它只用于没有身份文件的新资料；已有身份文件不会被默认值覆盖。

授权的身份上下文预算为最多 1,200 字符，默认龙妹设定可完整进入，超长自定义设定仍会有界截断；整个角色上下文默认最多 2,000 字符。凭证检查仍覆盖完整身份，预填文案避免将凭证标签写入安全说明而误触门禁。当前资料完整度与实际可验收范围见[龙妹聊天与记忆验收](龙妹聊天与记忆验收.md)。

## 聊天怎样形成闭环

“角色、记忆、知识、能力”在每次聊天中的职责必须分开：

1. **先处理本机确定答案**：身份问题、能力问题、记忆回顾和明确的“记住……”请求优先由本机规则处理，不调用在线模型。
2. **再组装在线上下文**：只把用户明确允许分享的身份资料、已确认且相关的用户记忆、已确认且相关的角色知识，以及实时能力状态放入本轮上下文。未确认、未授权、凭证类和无关内容不进入。
3. **最后带入有界聊天历史**：单条输入最多 1,200 字符，超限会拒绝并提示；文字聊天窗口只把最近最多 12 条、累计最多 6,000 字符的 user/assistant 消息传给模型，用于保持本轮连续性。在线请求失败时保留失败状态并提供“重试上次”，重试不会重复追加用户消息；关闭或清空窗口后不自动保存为长期记忆。
4. **需要长期记住时显式提交**：用户说“记住……”才进入本机规则判断。聊天和语音共用低风险自动保存、重复去重、冲突/敏感审核、凭证拒绝流程。

角色知识目前仍复用本地 Markdown 记忆记录的 `knowledge` 类型，但已经补充来源、引用和版本字段，并在角色与记忆窗口中随知识条目编辑、审核和确认。在线上下文会把这些元数据作为依据标签单独展示为“角色知识”，不与用户事实或偏好混写；元数据只是参考，不是模型指令。旧 schema 1 记忆读取时缺少这些字段会安全降为空值。同一来源、引用和版本下出现不同内容时会进入知识依据冲突审核；未完成审核的冲突条目不会进入在线上下文或本机知识回顾。在线检索会在排序取前 N 条之前先排除未授权、凭证类和未解决冲突条目，避免不安全候选挤占有限名额；角色知识的来源、引用和版本也参与本机相关性匹配。本机回顾同样不会展示含凭证关键词的旧记录。检索仍是保守关键词规则，不是语义或全文搜索。下一阶段再评估独立知识库、过期提醒和更强检索，不预先引入向量数据库。

## 一轮对话怎样工作

```text
用户说话 → 本机语音识别 → 读取该桌宠的身份、已确认记忆和实时能力
          → 只挑本轮允许分享的资料发给用户配置的在线模型
          → 桌宠显示/朗读回答 → 用户可选择把重要内容存为新记忆
```

记忆默认只留在本机，不会因为“存本地”就自动发给模型。要让模型使用某条记忆，用户必须在管理界面明确允许；应用先排除不具备发送资格的候选，再按本轮问题做本机相关性排序，最后最多带少量匹配项。这样不安全或无权限的条目不会占据有限上下文名额。筛选是保守、可解释的关键词匹配，并只加入少量中文别名归一化（例如“偏好/喜好/爱好”可匹配“喜欢”）；角色知识另外匹配来源、引用和版本字段。这不是通用语义理解，匹配不到就不发送记忆。语音转写本身仍会发给用户配置的在线服务，这是当前语音功能的既有边界。

“你是谁”由用户确认的身份资料回答；“你会什么”由应用实时能力清单回答，而不是让模型猜。当前未接入的直播平台、未配置的模型和不可用的语音能力都必须如实标成未启用。

## 用户怎样管理

新增一个“角色与记忆”窗口，先提供四个清楚的区域：

- **身份**：用户编辑角色名字、背景、性格、说话方式和边界；模型不能自行改写。
- **人格**：用户还可以编辑身份定位、核心价值观、愿望方向、与用户的关系，以及知识边界。这些字段共同组成角色的稳定行为约束。
- **记忆**：按事实、偏好、经历和知识查看；用户可新增、修改、删除，也可逐条决定是否允许在线模型使用。
- **能力**：显示应用当前实际状态，例如语音识别是否可用、在线模型是否配置、TTS 是否启用；这部分由应用生成，不能被角色文本覆盖。
- **目标**：用户可建立目标、编辑步骤、勾选进度、暂停/完成或删除。当前步骤由用户填写；后续再增加在线模型建议草案，发送前明确告知目标内容会交给所选服务商，返回结果先预览，用户确认后才保存。

首次填写可参考[龙妹角色资料示例](examples/龙妹角色资料/README.md)：身份示例已按当前 Markdown 格式写好，记忆明确标成待确认，目标只是可编辑草案。示例不代表真实共同经历；应用能力不手工写进角色资料，而由运行时状态生成。用户资料仍应通过窗口保存，不要用示例覆盖已有文件。

明确说“记住……”时，应用先在本机做有限规则判断：普通内容没有发现重复、冲突或敏感关键词时自动确认保存；完全重复的已确认内容不重复写入；可能冲突或涉及支付、医疗、身份资料等内容进入待审核；检测到密码、密钥、验证码等凭证时拒绝保存。手动在管理界面添加的记忆仍进入审核列表。自动确认只表示写入这台 Mac，不会开启在线分享。

凭证门禁同时检查记忆正文及来源、引用、版本字段；手动写入、编辑和确认也经过 Markdown 存储层的拒绝检查，命中时不创建或覆盖记忆文件，并向界面返回原因。新增记忆在提交前同步拦截，显示拒绝原因并保留输入，便于用户修正；编辑/确认失败也在窗口状态区显示存储层错误。身份资料仍可本机保存，但若已允许在线分享且任一身份字段命中凭证关键词，则整份身份上下文不发送，避免只删字段标签却意外外发其余关联内容。检测依然是有限关键词规则，不是凭证扫描器；旧文件仍可读取，但命中项不会进入在线上下文或本机回顾。

这些规则不是完整的隐私识别器：关键词可能漏掉敏感内容，也可能把普通语句误判为敏感。新记忆只接受用户明确说出的“记住……”指令，不从普通对话推测；用户可在本地记忆页检查、修改和删除。发生不确定、冲突或潜在高影响事项时，Agent 应暂停该项并请求人工判断，而不是猜测执行。

问“你记得我喜欢什么”时，本地会从已确认记忆中按关键词找相关内容；问“你记得什么”时才按最近记录概览。当前不做通用同义词理解、向量检索或自动总结，只覆盖少量显式别名；找不到时会明确说没有找到，不会编造答案。角色知识问题可在本机单独回顾已确认知识，也可按引用、来源或版本定位；待审核以及同一依据下尚未解决冲突的知识不会被当作已知事实，包含凭证关键词的旧记忆也不在回顾中展示。默认不保存整段聊天和录音，不自动从对话推测个人特征。删除记忆会删除对应文件，不留正文回收站；系统备份或用户云盘中的副本不由应用控制。

## 本地文件怎样保存

资料按稳定的桌宠实例 ID 分开保存。克隆桌宠不会复制原桌宠的私人记忆。

```text
~/Library/Application Support/AnimeDesktopPets/pets/<pet-id>/character/
  identity.md       用户掌控的角色身份
  memories/         一条记忆一个 Markdown 文件
  plans/            用户目标、步骤和进度；每个目标一个 Markdown 文件
```

`identity.md` 目前仍是一个文件，但已经按“身份定位、背景、性格、价值观、愿望、关系、表达方式、知识边界、行为边界”分节保存；旧版缺少新分节时按空值兼容读取，不会丢失原有身份。

Markdown 是唯一权威副本，用户可以直接查看、备份和通过应用修改。文件使用 front matter 保存版本、ID、时间、来源和分享设置；其中元数据采用 YAML 兼容的 JSON 写法，因此 macOS Foundation 可以离线稳定解析，不需要额外依赖。每条记忆正文只保存在 Markdown 正文；用户用文本编辑器修改正文后，应用也会读取修改后的内容。格式不认识或内容损坏时只报错，不擅自覆盖。第一版资料量小时直接读取文件；资料变多后才考虑 SQLite 全文索引，索引可删除重建，Markdown 仍是权威副本。

本地文件默认是明文，受 macOS 当前账户权限和用户的 FileVault 设置保护，不等于应用级加密。API Key 继续只放 macOS 钥匙串，不进入记忆文件。

## 代码怎样分工

继续使用 macOS 原生 Swift，不加 Node/TypeScript sidecar，也不改成 Tauri。当前产品只支持 macOS；Swift 已直接负责 AppKit、音频、钥匙串、窗口和进程管理。换成 TypeScript 不会减少这些原生工作，反而要额外维护 Node 运行时、跨进程通信和打包。只有未来平台目标改变，才重新评估桌面宿主，不为“可能跨平台”预先维护两套实现。

```text
apps/companion-macos/
  Sources/CharacterCore/       身份、记忆、能力等规则；不碰界面和磁盘
  Sources/CharacterMemory/     按 pet-id 读写 Markdown/front matter；负责校验和安全落盘
  Sources/CharacterUI/         SwiftUI 的身份、记忆、能力和目标界面
  Sources/DragonCompanion/     现有 AppKit 宿主；打开窗口并连接语音/模型
  Tests/                       每个模块各自的测试
apps/pet-runtime/              只画桌宠，不读身份或记忆
apps/speech-runtime/            只做本地 ASR/TTS，不接触模型 Key 和长期记忆
```

模块之间只通过小而明确的数据类型协作。界面、磁盘和模型网络请求各有边界；动画 helper 和语音进程不拥有角色资料。SwiftUI 按“身份、记忆、能力、目标”拆文件；跨页面重复使用的控件和样式才抽成公共组件。避免把新逻辑继续加进已经较大的 `Coordinator.swift`，也不为拆分而制造没有实际职责的层。

## 为什么不直接接 Agent 框架

GitHub 项目提供的是可选设计，不是可以原样搬来的整套答案：OpenClaw 将用户资料、精选长期记忆和按日记录分层保存，并提供按需搜索；Hermes Agent 也区分用户资料和 Agent 记忆，并支持审批；Letta 展示了 Agent 持久状态和工具审批的设计方向。这些项目的自动化、索引和运行环境都与本项目的隐私边界不同。我们采用“资料分开、Markdown 可检查、需要时再检索”的方向，并只对明确记忆指令开放低风险自动保存；高影响、不确定或外部副作用事项仍必须暂停并请求人工审核，不照搬默认自动写入或云端 Agent 状态。

通用动作按宿主登记的类型分类，而不是让模型自己声明风险：只读角色资料目录可自动执行，不得扩展成任意文件读取；明确提出的、仅本机且由宿主确认可撤销的记忆/目标操作可自动执行；写入若不是用户明确要求、撤销性未知、删除或修改角色身份时需确认；联网请求必须来自用户明确发起的一轮对话；对外发布、支付、权限变化和未知动作一律不得自动执行，须停下来审核；凭证访问直接拒绝。宿主为每次请求签发短时效、一次性上下文，执行前检查来源、审批、过期时间和重放状态；人工审批不能按动作名称另造凭证，必须引用同一发行器签发的原始待审核请求，并且只能续签一次；模型只能生成建议，不能制造这个上下文。当前已有纯策略、签发和单元测试，尚未接入任何通用工具执行器，因此这张规则表是后续执行器的门禁，不代表桌宠已能自主操作文件、账户或外部服务。

本项目先自己实现最小能力，不引入 Letta、Mem0、LangGraph、Graphiti、向量数据库或后台 Agent。后续通用对话应先按当前问题从本机筛选记忆，再从筛选结果中排除未确认或未授权项；不能因为一条资料获准分享，就把它无关地附到每个请求。第一阶段用小规模文件和显式身份/能力问答验证闭环；在扩大语音使用前，必须完成相关性筛选与模拟 HTTP 请求测试。资料变多后，再用真实问题样本评估本机全文搜索是否足够。第三方项目会变化，未来引入依赖前要重新确认许可证、数据流和维护状态。

## 分阶段交付

1. **资料底座**：身份、记忆和目标计划使用 Markdown，按桌宠隔离并安全读写。
2. **可管理、可回答**：SwiftUI 管理人格、记忆、能力和用户计划；常见身份/能力/记忆问题本地回答；在线对话只携带明确授权且与问题相关的少量记忆。
3. **明确记忆**：识别“记住”请求；低风险普通内容可自动保存，重复项去重，冲突/敏感项进入待审核，凭证类内容拒绝保存；支持用户检查、编辑、确认、删除和重启后读取。
4. **计划建议**：用户在目标编辑器主动请求时，先确认目标名称和说明将发送给服务商且请求可能产生费用；在线模型仅返回最多12条步骤草案。草案经过格式和长度校验后回填编辑器，由用户审核、修改并手动保存。请求不附带人格或记忆，也不自动执行任何步骤。

步骤草案只使用 OpenAI-compatible Chat Completions 普通 JSON 文本约定，不依赖供应商专有 JSON mode；服务端格式错误、字段超限或返回过大时均失败关闭。该路径已通过模拟 HTTP 回归，未发真实请求；不同服务商的模型指令遵循质量仍需用户自行选择服务后验收。

每一步都先有离线测试，再接到应用。测试使用合成资料和模拟 HTTP，不使用真实 Key、不产生费用。是否启动应用、使用麦克风或发真实模型请求，仍由用户明确选择。直播平台接入和独立发行包中的语音环境/模型是后续工作，不属于以上步骤已完成的内容。

## 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 模型把猜测写成事实 | 只有明确“记住……”才进入记忆判断；模型不能自行生成长期记忆 |
| 低风险自动化越权 | 只对明确“记住”指令做本地规则判断；支付、医疗、身份、冲突和未知情况暂停并请求人工审核 |
| 凭证落入长期记忆或在线请求 | 密码、密钥、验证码、Token 等命中规则时拒绝保存；即使旧文件误开分享也不进入在线上下文；不读取或保存 API Key |
| 私人记忆意外发给服务商 | 记忆默认本地；逐条授权分享；请求测试检查实际发送内容 |
| 桌宠夸大自身能力 | 能力状态由应用实时提供，模型不能改写 |
| 多桌宠资料串在一起 | 每个 `pet-id` 独立目录；克隆不复制记忆 |
| 提示注入或资料中含指令 | 记忆只作为资料，不授予工具权限；工具仍由宿主控制 |
| 文件损坏或格式升级 | 校验版本、原子写入；未知格式只读并保留原文件 |

## 参考项目

- [OpenClaw 记忆说明](https://docs.openclaw.ai/concepts/memory)：区分用户资料、精选长期记忆和按日记录，详细记录按需检索；在线模型请求会将选中的资料交给服务商。
- [Hermes Agent 记忆说明](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)：区分用户资料和 Agent 记忆，支持审批；默认允许自动写入。
- [Letta](https://github.com/letta-ai/letta)：参考持久 Agent 状态的概念；其服务端 Agent 模型不等于本机桌宠存储。
- [Mem0](https://github.com/mem0ai/mem0) 与 [LangMem](https://github.com/langchain-ai/langmem)：记忆提取、更新和检索概念；不是本项目首期的必需依赖。
